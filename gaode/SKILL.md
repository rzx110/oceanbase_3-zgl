# 周边去哪儿

把用户的“附近去哪儿”变成有真实地点、有步行路线依据的简洁推荐。只使用本次高德工具返回的数据作事实依据；每个地点都是从同一起点出发的独立备选，不串成多站行程。

## 1. 提取需求

- 记录城市、起点名称和原始坐标、地点类型/关键词、步行时间上限、推荐数量、硬性限制和软偏好。坐标按工具要求传入，通常为 `经度,纬度`，不要交换顺序、擅自移动起点或把地铁站中心替代明确的出口坐标。
- 用户要求 N 个时取 `K = min(N, 3)`；未指定数量时最多 3 个。“最多”“不超过”不是必须凑满。没有给时间上限时不要自行添加“15 分钟”条件。
- “优先近一点”用于排序；“步行不超过 15 分钟”是硬性上限，等于 15 分钟可接受。“少于 15 分钟”则严格小于。保留用户其他明确排除条件。
- 评测会给出起点坐标，直接使用，不询问设备定位或 API Key。实际用户确实缺少必要起点且无法确定时，才简短询问，不猜测位置。

## 2. 搜索真实地点

1. 优先使用当前环境提供的高德 MCP **周边搜索**工具。先查看该工具的参数说明，传入原始起点 `location`、相关 `keywords`、可用的地点类型筛选；支持城市过滤时带上城市。若环境只提供关键词地点搜索，按城市和类别搜索，再用候选真实坐标核验步行路线，不将全城搜索顺序当成周边远近。工具名称可能带不同前缀，以当前工具 schema 为准，不调用不存在的接口。
2. 用户限定搜索半径时遵守该范围。否则可先查约 2 千米的周边；搜索半径只是候选范围，不能作为步行距离或时间证明。关键词应匹配真实类别，例如“安静的咖啡馆”先搜“咖啡馆”，不要把整句偏好当作唯一关键词造成无结果。
3. 保留候选的 POI ID、原始名称、完整地址、坐标、城市/区域、类型及查询返回的相关属性。按 POI ID 去重；缺少 ID 时结合名称、地址和坐标判断，不能把同品牌不同分店合并或混用它们的数据。排除已知城市或类型不符的结果。
4. 名称、地址或坐标缺失时，若提供高德详情工具，可按该 POI ID 补查；不能从地名常识补写地址或编造坐标。最终推荐必须能与同一真实 POI 对应。地址仍不可用的候选不列入正式推荐。
5. 结果太少时，可按需作一次同类别关键词调整或扩大一次候选半径；不突破用户明确的区域、半径、类型限制，步行时间上限始终保留。扩大后仍不足就少推荐。不要无限搜索，也不要用网页、模型记忆或示例地点填补高德结果。

## 3. 逐个查询步行路线

- 对准备筛选的每个候选，调用高德 MCP **步行路径规划**：`origin` 始终是用户原始起点，`destination` 是这个 POI 的已验证坐标。不要把前一个推荐作为下一条路线的起点。
- 通常先核验约 6–10 个相关候选；结果少时核验现有候选，遇到超时/路线失败可继续查其他候选，直到获得合理备选、候选用尽或工具预算不允许。搜索返回的距离仅用于安排候选查询顺序，不能用它代替步行路线，也不要宣称已找到全城最优。
- 使用同一条有效步行方案的总距离和总耗时；若返回多条方案，选其中满足用户条件且与偏好一致的一条。优先使用路径级总值，不把不同方案的最短距离与最短时间拼接，不以驾车/骑行路线、直线测距或估算步速替代步行数据。
- 按工具说明读取数值与单位。若返回的是标准 `distance` 米、`duration` 秒，把字符串解析为数值；T 分钟的上限换成 `60 × T` 秒比较。字段缺失、无有效路径、单位无法确认或数值异常时，该候选的步行条件尚未验证，不列入正式推荐。工具真实返回的有效 0 距离/耗时不凭空改写。
- **先用未舍入的原始耗时筛选，再格式化展示。** 例如上限 15 分钟，900 秒可入选，901 秒不可入选；不能把 15 分 1 秒四舍五入为 15 分钟后放行。若用户另有步行距离上限，同样用原始路线总距离比较。可显示“14 分 36 秒”，若只显示整数分钟则向上取整。距离优先显示原始米数，较长距离可附近似公里数。

## 4. 筛选、排序与理由

1. 先满足地点类型、城市/区域、数量、步行时间及其他可核实的硬条件，不能为凑满数量推荐超时地点。最终地点必须同时有地点搜索/详情依据和有效步行路线依据。
2. 用户优先“近”时，按**步行路线距离升序**，相同距离按耗时升序；优先“快”或未指定其他排序时，按**步行耗时升序**，相同耗时按距离升序。若有其他偏好，只在已有数据支持且满足硬条件的候选间调整，并让理由与排序一致。
3. 安静、座位、插座、排队、营业状态、价格等属性，只有工具明确提供对应信息时才引用，并保留其时效边界。缺少依据就写“未核实”；不能由店名、评分、品牌或地点类型推断。“安静优先”无法核实时可按距离排序并说明；如果用户把该属性作为必须条件，则说明无法核实，不能声称已满足全部条件。
4. 理由简短、可验证，例如“本次已核验候选中步行距离最短，符合咖啡馆类别”。不要添加“人少安静”“正在营业”“口碑最好”等无数据支撑的宣传语。

## 5. 返回结果及异常处理

有符合条件的结果时，简短交代起点和筛选条件，再用表格或列表返回不超过 K 个地点：

| 地点 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |

表格逐行填入本次工具数据及有依据的理由，不使用固定地点示例。时间注明来自高德步行路线预估，各行均从同一起点出发。正文不用倾倒原始 JSON、工具日志或内部推理。

- **数量不足**：给出实际符合数量，说明“本次查询范围内只核验到 X 个符合条件的地点”，简述是超时、类型不符还是路线无法核实；不把局部搜索无结果说成城市里绝对没有。
- **零个符合**：直接说明本次未查到符合条件的地点，不输出虚构推荐。可以建议放宽时间/范围或换类别，但本轮不自动放宽硬条件，不把超限地点混进符合条件列表。
- **信息缺失**：对偏好属性统一补一句“安静程度/排队/营业状态等未核实”，不要以免责声明掩盖编造的肯定描述。
- **工具异常**：对临时超时或服务错误，在运行预算内用相同参数重试一次；认证、权限或参数错误不要盲目重试。个别路线失败时可保留其他已验证结果并说明不足；地点搜索或所有路线都失败时，明确说服务异常导致本轮无法核实推荐，不假装已经查过或用估计数值顶替。

交付前自查：每一行是否对应同一真实 POI？路线是否都始于给定起点？原始耗时是否满足上限？条数是否不超过 K？排序与路线数据是否一致？无法核实的属性是否明确标注？修正后再回答。

高德能力参考：[MCP Server 官方说明](https://developer.amap.com/api/mcp-server/summary)。运行环境及密钥由调用方配置，本 Skill 不包含密钥、预置地点或独立服务依赖。
